## Commands

Run from the repo root. Python always goes through `uv run`, never `python`/`python3`.

| Task | Command |
|---|---|
| Install everything, including the lefthook pre-commit hook and Playwright's Chromium | `uv sync` then `npm install` |
| Backend, the agent's service and dashboard, on the ports in `settings/.env.defaults` (8000, 8002 and 5173) | `npm run dev` (the backend alone: `uv run -m backend`; the service: `uv run -m agent.service`) |
| Every check (what to run before handing work over) | `npm run check` |
| Python checks: ruff format, ruff lint, pyright, pytest with 80% coverage | `npm run check:python` |
| TypeScript checks: prettier, ESLint, tsc, vitest with 80% coverage | `npm run check:ts` |
| End-to-end tests (start their own backend on 8001, dashboard on 5174 and a stand-in for the agent's service on 8003, with a fresh `e2e/undercover-e2e.db`; those ports must be free) | `npm run e2e` |
| Format everything | `npm run format` |
| Run the agent on one claim, outside any run, on a model (calls the model; needs `DATABASE_URL` for its saved progress). Dispatches and evaluations are started on the dashboard | `uv run -m agent CLM-1001`, `uv run -m agent CLM-1001 --model anthropic:claude-haiku-5-5` |
| Reset the database to `data/` (Supabase when `.env` has `DATABASE_URL`) | `uv run -m backend.seed` |
| One Python test | `uv run pytest agent/tests/test_harness.py::test_work_claim_approves_and_the_graph_pays --no-cov` |
| One vitest file | `npx vitest run --root dashboard src/App.test.tsx` |
| One Playwright test | `npx playwright test e2e/claims.spec.ts` |
| Postman collection against the dev backend (reset the data first) | `npx -y newman@6 run backend/postman/undercover.postman_collection.json -e backend/postman/undercover_local.postman_environment.json` |

`--no-cov` matters for single Python tests: `pyproject.toml` adds `--cov` with `fail_under = 80`, so a partial run fails on coverage otherwise. pyright is the npm package (`npx pyright`), configured to use `.venv`.

The pre-commit hook runs `check:python` when Python files (`backend/`, `agent/`, `tests/`), `*.toml`, `settings/.env.defaults`, `backend/postman/` or `dashboard/src/api.ts` are staged and `check:ts` when `dashboard/`, `e2e/`, `*.config.*` or `settings/.env.defaults` files are staged. Never bypass it with `--no-verify`, and never lower thresholds or disable lint rules to get a green run (`docs/PROCESS.md`).

## Architecture

The product is three parts that talk only over HTTP, plus e2e tests:

- `backend/`: FastAPI app (`backend.main:app`), run with `uv run -m backend`. Every route under `/api` has an `operation_id`, a one-line docstring and no optional inputs (`docs/TECH_STACK.md`), because the agent's tools are built against this API. The store is SQLAlchemy Core (`backend/db.py`, queries in `backend/store/`), on Supabase's Postgres when `DATABASE_URL` is set (schema `undercover`, at most `DATABASE_CONNECTIONS` per process, waiting up to `DATABASE_WAIT_SECONDS` for one) and SQLite otherwise, as in the tests. The app keeps `BACKEND_THREADS` threads (`main.py`'s lifespan), since a request waits on a thread for a connection and its route needs another. `backend/workflow.py` holds the agent's moves on a claim and `backend/reviews.py` the handlers' (`review_payout`: a sign-off or a rejection with a note), both following `backend/claim_rules.py` (the $1,000 sign-off rule, what happens after a rejection, no review or decision on an evaluation's copy): the backend enforces them, so the agent can't bypass them. A repeat of a decision or payment counts as done, and a claim's `revision` makes sure two at once are recorded once. After a review is committed, a background task calls the agent's service through `backend/agent_service.py`, which also starts dispatches and evaluations and stops them, writing nothing. `backend/api.py` has what routes share (the per-request database, `load_claim`, `queue_line`). `main.py` only puts the app together from one router per resource: `claims.py` (with `calculate_payout`, rules in `payout.py`), `records.py`, `documents.py`, `workflow.py`, `usage.py` (each model call and spell of work on a claim), `reviews.py`, `runs.py` (dispatches: `create_dispatch`, `record_run_claims`, `finish_run` with its summary, `stop_runs`, `get_latest_dispatch`, and the dashboard's `start_dispatch` and `stop_run`; `run_views.py` builds a run as the API shows it), `evaluations.py` (copies of a labelled set, scored when read with `scoring.py`), `agent_models.py` (`list_models`) and `insights.py`. All SQL is in `backend/store/` (`claims.py`, `records.py`, `steps.py`, `runs.py`, `usage.py`, `evaluations.py`, the only reader of the handlers' decisions); `db.py` holds the schema. Only `seed.py` reads `data/evals/`. Claims start in a run or on their own (`start_claim` takes `run_id`, which may be null, and `thread_id`); tests start them with `backend/tests/claim_starts.py`.
- `agent/`: the UnderCover Agent, in five parts (`docs/CODE_STANDARDS.md` 13). `api.py` is the only way to the backend: one function per operation, named after it, at `UNDERCOVER_API`; a 4xx raises `api.Refused`, and a refused connection is tried again five times. `tools.py` holds the tools; a claim agent's tools read the claim from `ToolRuntime[ClaimContext]` (its run or `None`, the claim and its thread), and `decide_claim` returns a `Command` that puts the backend's status in the graph's state. The claim agent is a hand-written LangGraph graph (`graph.py`: `agent`, `tools` (`ToolNode` with `wrap_tool_call` recording results and `handle_tool_errors` turning refusals into text), `wait_for_sign_off` (`interrupt()`; resumed with the handler's review: a sign-off goes to `pay`, a rejection takes the note back to `agent`) and `pay`); its nodes record steps and each model call's tokens and cost through `recording.py`, the model call is retried with `with_retry`, and the 30-call limit is in the state. It saves after every step with the synchronous `PostgresSaver`: `checkpoints.pool()` opens the process's `psycopg_pool` pool on `DATABASE_URL` and `checkpoints.saver(pool)` gives each claim run a saver of its own. `harness.py` builds the model with `init_chat_model` and the claim graph, works a claim with `work_claim(claim_id, run_id, model, saver, llm=None)` (a new attempt on a new thread), picks one up with `carry_on(claim_id, run_id, model, saver, llm=None)`, and times each spell of work; `work_in_run(claim_id, run_id, model, new_saver, llm=None)` does whichever a claim needs and is the one way the dispatcher reaches the claim agent. `harness.TRANSIENT` (rate limits and timeouts) is raised without settling the claim. `dispatcher.py` is a LangGraph graph with no model (`list_claims`, a `Send` per claim to `work_claim` with a `RetryPolicy`, `finish_run`, `max_concurrency` set to N); its tests take the waits out of `RETRY` with an autouse fixture. `service.py` is the agent's service (FastAPI, `UNDERCOVER_AGENT`, started by `npm run dev`): `start_dispatch` and `start_evaluation` (one run at a time, on a thread of its own), `stop_run` (graceful) and `resume_claim`. `tracing.py` traces the claim agents in Langfuse with its LangChain `CallbackHandler`, from the keys in `.env`: each piece of work on a claim is a `work-claim` or `carry-on` trace of its own (run in a fresh `contextvars.Context`, which also keeps the claim graph from being taken for a subgraph of the dispatcher), in the session named after the claim's thread, tagged `run-N` with its run. The agents are named in traces with `run_name` in the invoke config. Tests turn tracing off in the root `conftest.py`, which also gives every test an in-memory saver in place of Postgres; the `traces` fixture in `agent/tests/conftest.py` sends spans to memory. `config.py` reads `settings/models.toml`; settings come from the `settings` package (`settings/__init__.py`). `agent/__main__.py` is the command line, for one claim.
- Dispatches and evaluations: the dashboard's forms call the backend's `start_dispatch` or `start_evaluation`, which ask the agent's service; the service creates the run through the backend and hands it to the dispatcher. An evaluation works its own copies of a labelled set's claims (`CLM-1104-E7`), which the queue, Insights and dispatches leave out and nobody can review; a copy held for sign-off counts as finished and its saved progress is cleared.
- `dashboard/`: React + Vite + TypeScript (strict, no `any`). The keys of `api` in `api.ts` are the backend's operation ids in camelCase. Vite proxies `/api` to `UNDERCOVER_API`, so the dashboard calls relative `/api/...` URLs. Pages are routed by the URL hash (links and `parseRoute` in `paths.ts`, `useRoute` in `hooks.ts`), data is loaded with `usePoll` (refreshes on an interval and pauses when the tab is hidden; with no interval it loads once, retrying every 5 seconds until a load succeeds), and every API call goes through `api.ts`; the types it returns are in `claimTypes.ts` and `agentTypes.ts`, re-exported from `api.ts`. The queue page's dispatch form is `DispatchForm.tsx` and the latest dispatch `DispatchPanel.tsx`, with its arithmetic and summary lines in `runs.ts` (and `MAX_AGENTS`, which Vite defines from `settings/.env.defaults`); the Scoreboard is `Scoreboard.tsx`, an evaluation's page `EvaluationPage.tsx`, with their formatting in `evaluations.ts`. Brand tokens and the light and dark themes are CSS variables in `styles.css`. Tests stub `fetch` with `mockFetch` from `testing.ts`, keyed by `"METHOD /path"`. ESLint is strict: props are `Readonly<>`, no nested ternaries, no numbers in template strings without `String()`.
- `e2e/`: Playwright on its own ports and database (`playwright.config.ts`; the dashboard's proxy target comes from `UNDERCOVER_API`). Tests set up the agent's decisions, dispatches and evaluations through the API, so no model is called; a stand-in for the agent's service (`e2e/agent-stand-in.ts`) records the resumes, starts and stops it's asked for, which the tests read through `e2e/stand-in.ts`.
- `backend/postman/`: the API's Postman collection and environment. Add every new or changed endpoint to the collection.

Configuration (`docs/CODE_STANDARDS.md` 22): the `settings/` folder loads the env files: `settings/__init__.py` for Python (imported as `settings`) and `settings/settings.config.ts` for TypeScript. `settings/.env.defaults` (committed) holds every setting that isn't secret, with `${NAME}` for values built from others, `.env` the keys and overrides, and `settings/models.toml` the models allowed with prices. No host, port, URL, model id or price is written in code; `tests/test_standards.py` and `dashboard/src/standards.test.ts` fail if one is. The root `conftest.py` makes tests read `settings/.env.defaults` alone, and so does the e2e run.

Testing pattern for the agent (see `agent/tests/test_harness.py` and `test_graph.py`): tests never call a real model. They pass a `StubModel` (a `GenericFakeChatModel` whose `bind_tools` returns itself) with scripted `AIMessage`s, including tool calls, as `llm`, with the `memory_saver` fixture as the saver; the autouse fixture in `agent/tests/conftest.py` monkeypatches `api.client` to return FastAPI's `TestClient(app)` so the agent's tools hit the real backend in-process, and stubs the backend's call to the agent's service. A restart is a stub that raises `KeyboardInterrupt` (`test_restart.py`). Claim agents working side by side get a `ByClaim` stub (`agent/tests/stub.py`), a script for each claim chosen by the claim its thread starts with (`test_dispatcher.py`).

Data: `data/` is the business data the backend seeds from. `data/evals/` is the answer key: the agent must never see it, and don't open it unless asked. `context/` holds data governance's files, which become the context layer on Week 3 Day 3.

`docs/STATUS.md` describes what is built and how to run it; keep it current as the build grows, since the skeleton above is replaced build by build.
