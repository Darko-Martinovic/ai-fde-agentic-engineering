# Tech stack

- `backend/`: FastAPI with SQLAlchemy Core, on Supabase's Postgres (the session pooler in `DATABASE_URL`, the `undercover` schema, at most 4 connections a process, waiting up to 25 seconds for one, with 200 threads for requests, since each waits on a thread for a connection and its route runs on another) and on SQLite in the tests, each query written once for both. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Routes live in one router per resource; the runs router holds the dispatches and the evaluations router the evaluations, scored when they're read (`scoring.py`, the lab's measures). Paying a claim is a separate operation that takes the amount; a repeat of a decision or payment already recorded counts as done. A handler's review of a held payout (`review_payout`, a sign-off or a rejection with a note) is handed to the agent's service, at `UNDERCOVER_AGENT`, by a background task once it is committed; starting a dispatch or an evaluation and stopping it go to the service too, through `agent_service.py`, which writes nothing. `calculate_payout` applies UnderCover's payout rules. Only seeding reads `data/evals/`, into tables no claim operation reads. Handlers sign in through Supabase Auth: `auth.py` checks an access token's ES256 signature against the project's keys with PyJWT's `PyJWKClient`, and `signed_in.py` gives a route the handler, through FastAPI's `HTTPBearer`, and refuses an action over the limit to a handler who can't sign off over it. The configuration's versions (`configuration.py`), the platform's settings (`platform_settings.py`, one row per change) and the rounds of improvement (`improvement.py` for the dashboard, `rounds.py` for the agent's service, with `round_rules.py`, `round_views.py`, `verdict.py`, `version_scores.py` and `spending.py`) are records in the same database; `diffs.py` finds what changed with `difflib`. The judge (`judge.py`) is Jev on OpenRouter's Decisions endpoint through the `openrouter` package, at `JUDGE_URL`: `finish_run` grades an evaluation's copies on threads of their own after letting go of its database connection.
- `agent/`, in six parts: `api.py` is the only way the agent reaches the backend, one function per operation; `tools.py` holds every tool, and each tool reads what it needs, such as the claim a claim agent is working on, from `ToolRuntime`; `harness.py` builds the model and the claim graph and works a claim: `work_claim(claim_id, run_id, version, saver)` as a new attempt on a new thread, `carry_on(claim_id, run_id, version, saver)` from its saved progress, and `work_in_run`, the one function the dispatcher calls, which does whichever the claim needs with a saver of its own; `dispatcher.py` is a LangGraph graph with no model, as in `labs/week2day4.ipynb`: a node that lists the claims, a `Send` per claim, a worker with a `RetryPolicy` on `ModelRateLimitError` and `ModelTimeoutError` (the harness lets those through without settling the claim, so a retry carries it on), `max_concurrency` set to N, and a node that finishes the run once every claim is back; `service.py` is the agent's service (FastAPI at `UNDERCOVER_AGENT`, started by `npm run dev`), which starts dispatches, evaluations and rounds of improvement, one at a time under a lock that names what holds it, on threads of their own, stops a run gracefully, passes a handler's review on to the improver and picks a claim back up after a handler's review; and `improver.py` is the improver, a LangChain `create_agent` on GPT-6 Luna at medium (`IMPROVER_MODEL`), with the lab's four tools, `HumanInTheLoopMiddleware` on its two proposals, `ModelCallLimitMiddleware` at 20 calls a round, a `before_model` hook that ends a stopped round's stretch and a `wrap_model_call` that records each call with the round; its progress is saved on the round's thread, so a round waiting for a handler survives a restart. `rounds.py` works a round in the service, and `improver_api.py` is the improver's way to the backend. The claim agent is a LangGraph graph of our own (`graph.py`: its state, an `agent` node that calls the model with the tools bound, LangGraph's `ToolNode`, a `wait_for_sign_off` node that pauses with `interrupt()` and a `pay` node), whose progress is saved after every step by LangGraph's synchronous Postgres checkpointer (`checkpoints.py`, `durability="sync"`) in the same schema: a `PostgresSaver` for each claim run on the process's pool of 4, since one saver lets a single read or write through at a time. Each claim keeps its own thread, never a subgraph of the dispatcher. The graph's nodes record each reply, tool call, tool result and section read, and each model call's tokens, cost (OpenRouter's `usage.cost`, or nothing for a local model) and time, on the claim with its run (`recording.py`); the harness records each spell of work. `tracing.py` traces each piece of work on a claim in Langfuse through its LangChain `CallbackHandler`, a trace of its own (`work-claim` or `carry-on`) in the session named after the claim's thread, tagged with its run (`langfuse_tags`). `versions.py` holds a version of the claim agent's configuration as the harness builds it, and `connection.py` the one connection to the backend. Each claim agent is built from a version of its configuration (its instructions, model and reasoning effort), which the backend keeps: models come through `init_chat_model` from OpenRouter, the models allowed being listed in `data/models.json` with their reasoning efforts, prices and options, and version 1 is `openai/gpt-6-luna` at low reasoning effort as the brief asks. A student on free models sets `MODEL_NAME` (OpenRouter's free models or a local Ollama), which is then the only model allowed.
- `dashboard/`: React, Vite and TypeScript. It calls the backend only through `api.ts`, at relative `/api` URLs that Vite proxies to `UNDERCOVER_API`, with the signed-in handler's access token from `@supabase/supabase-js` (`auth.ts`). Pages are in `pages/`, shared parts in `components/`; the charts are SVG, with no chart library.
- `e2e/`: Playwright tests, on their own ports and database, with stand-ins for the agent's service, Supabase Auth and the judge, and each handler's browser storage kept by a setup project (`storageState`).
- `data/`: the business data the backend starts from. The agent never sees `data/evals/`, which holds the answer key; seeding stores it apart for the scoreboard.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26.

Settings: `settings/.env.defaults` (committed) holds every setting that isn't secret, such as `UNDERCOVER_API`, `UNDERCOVER_AGENT` and the ports, with `${NAME}` for values built from others; `.env` holds the keys (`OPENROUTER_API_KEY`, `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `DATABASE_URL`), the Supabase project handlers sign in through (`VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`) and the handlers' password for browser checks (`HANDLER_PASSWORD`), and any overrides, such as a free `MODEL_NAME`; `settings.py` and `settings.config.ts` read both. No address, port, model id or price is written in code.
