# Tech stack

- `backend/`: FastAPI with SQLAlchemy Core, on Supabase's Postgres (the session pooler in `DATABASE_URL`, the `undercover` schema, at most 4 connections a process, waiting up to 25 seconds for one, with 200 threads for requests, since each waits on a thread for a connection and its route runs on another) and on SQLite in the tests, each query written once for both. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Routes live in one router per resource; the runs router holds the dispatches and the evaluations router the evaluations, scored when they're read (`scoring.py`, the lab's measures). Paying a claim is a separate operation that takes the amount; a repeat of a decision or payment already recorded counts as done. A handler's review of a held payout (`review_payout`, a sign-off or a rejection with a note) is handed to the agent's service, at `UNDERCOVER_AGENT`, by a background task once it is committed; starting a dispatch or an evaluation and stopping it go to the service too, through `agent_service.py`, which writes nothing. `calculate_payout` applies UnderCover's payout rules. Only seeding reads `data/evals/`, into tables no claim operation reads.
- `agent/`, in five parts: `api.py` is the only way the agent reaches the backend, one function per operation; `tools.py` holds every tool, and each tool reads what it needs, such as the claim a claim agent is working on, from `ToolRuntime`; `harness.py` builds the model and the claim graph and works a claim: `work_claim(claim_id, run_id, model, saver)` as a new attempt on a new thread, `carry_on(claim_id, run_id, model, saver)` from its saved progress, and `work_in_run`, the one function the dispatcher calls, which does whichever the claim needs with a saver of its own; `dispatcher.py` is a LangGraph graph with no model, as in `labs/week2day4.ipynb`: a node that lists the claims, a `Send` per claim, a worker with a `RetryPolicy` on `ModelRateLimitError` and `ModelTimeoutError` (the harness lets those through without settling the claim, so a retry carries it on), `max_concurrency` set to N, and a node that finishes the run once every claim is back; and `service.py` is the agent's service (FastAPI at `UNDERCOVER_AGENT`, started by `npm run dev`), which starts dispatches and evaluations, one at a time, on threads of their own, stops one gracefully and picks a claim back up after a handler's review. The claim agent is a LangGraph graph of our own (`graph.py`: its state, an `agent` node that calls the model with the tools bound, LangGraph's `ToolNode`, a `wait_for_sign_off` node that pauses with `interrupt()` and a `pay` node), whose progress is saved after every step by LangGraph's synchronous Postgres checkpointer (`checkpoints.py`, `durability="sync"`) in the same schema: a `PostgresSaver` for each claim run on the process's pool of 4, since one saver lets a single read or write through at a time. Each claim keeps its own thread, never a subgraph of the dispatcher. The graph's nodes record each reply, tool call, tool result and section read, and each model call's tokens, cost (OpenRouter's `usage.cost`, or the prices in `settings/models.toml`) and time, on the claim with its run (`recording.py`); the harness records each spell of work. `tracing.py` traces each piece of work on a claim in Langfuse through its LangChain `CallbackHandler`, a trace of its own (`work-claim` or `carry-on`) in the session named after the claim's thread, tagged with its run (`langfuse_tags`). `config.py` reads `settings/models.toml`. Models come through `init_chat_model` from OpenRouter, Anthropic or a local Ollama, each one listed in `settings/models.toml` with its price and options; the default is `MODEL_NAME`, `openai/gpt-6-luna` on OpenRouter at low reasoning effort as the brief asks, and the dashboard's forms or `--model` pick another.
- `dashboard/`: React, Vite and TypeScript. It calls the backend only through `api.ts`, at relative `/api` URLs that Vite proxies to `UNDERCOVER_API`.
- `e2e/`: Playwright tests.
- `data/`: the business data the backend starts from. The agent never sees `data/evals/`, which holds the answer key; seeding stores it apart for the scoreboard.
- `bench/`: the model comparison, apart from the product, which runs its trials as evaluations through the backend.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26.

Settings: `settings/.env.defaults` (committed) holds every setting that isn't secret, such as `UNDERCOVER_API`, `UNDERCOVER_AGENT` and the ports, with `${NAME}` for values built from others; `.env` holds the keys (`OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY`, `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `DATABASE_URL`) and any overrides, such as `MODEL_NAME`; `settings.py` and `settings.config.ts` read both. No address, port, model id or price is written in code.
