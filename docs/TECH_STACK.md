# Tech stack

- `backend/`: FastAPI with SQLAlchemy Core, on Supabase's Postgres (the session pooler in `DATABASE_URL`, the `undercover` schema, at most 3 connections a process) and on SQLite in the tests, each query written once for both. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Paying a claim is a separate operation that takes the amount; a repeat of a decision or payment already recorded counts as done. A handler's review of a held payout (`review_payout`, a sign-off or a rejection with a note) is handed to the agent's service, at `UNDERCOVER_AGENT`, by a background task once it is committed. `calculate_payout` applies UnderCover's payout rules.
- `agent/`: the claim agent is a LangGraph graph of our own (`graph.py`: its state, an `agent` node that calls the model with the tools bound, LangGraph's `ToolNode`, a `wait_for_sign_off` node that pauses with `interrupt()` and a `pay` node), whose progress is saved after every step by LangGraph's synchronous Postgres checkpointer (`checkpoints.py`, `durability="sync"`) in the same schema; the queue agent is LangChain's `create_agent` (`queue_agent.py`). `api.py` is the only way the agent reaches the backend, one function per operation. `tools.py` holds every tool, and each tool reads what it needs, such as the claim a claim agent is working on, from `ToolRuntime`; the claim agent pays nothing itself: the graph pays an approval, at once or after a handler's sign-off, when the backend says it can. The graph's nodes record each reply, tool call, tool result and section read on the claim, and each model call's tokens, cost and time on the run (`recording.py`), as middleware did; the queue agent keeps LangChain's middleware (`middleware.py`) for its usage, refusals, retries and call limit. `harness.py` builds the model and the claim graph: `work_claim(claim_id, run_id, model, saver)` works a claim as a new attempt on a new thread, and `carry_on(claim_id, run_id, model, saver)` picks its thread up from its saved progress, after a handler's review or a restart; every run first carries on the claims left in progress. The agent's service (`service.py`, a small FastAPI app at `UNDERCOVER_AGENT`, started by `npm run dev`) picks a claim back up after a handler's review. `tracing.py` traces the agents in Langfuse through its LangChain `CallbackHandler`: each piece of work on a claim is a trace of its own (`work-claim` or `carry-on`) in the session named after the claim's thread, so a claim's work before and after a pause or a restart is found together, and a queue run is one trace; LangChain's middleware hooks aren't sent. `config.py` reads `settings/models.toml`. Models come through `init_chat_model` from OpenRouter, Anthropic or a local Ollama, each one listed in `settings/models.toml` with its price; the default is `MODEL_NAME`, `deepseek/deepseek-v4.1-flash` on OpenRouter as the brief asks, and the dashboard or `--model` picks another.
- `dashboard/`: React, Vite and TypeScript. It calls the backend only through `api.ts`, at relative `/api` URLs that Vite proxies to `UNDERCOVER_API`.
- `e2e/`: Playwright tests.
- `data/`: the business data the backend starts from. The agent never sees `data/evals/`, which holds the answer key.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26.

Settings: `settings/.env.defaults` (committed) holds every setting that isn't secret, such as `UNDERCOVER_API`, `UNDERCOVER_AGENT` and the ports, with `${NAME}` for values built from others; `.env` holds the keys (`OPENROUTER_API_KEY`, `ANTHROPIC_API_KEY`, `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, `DATABASE_URL`) and any overrides, such as `MODEL_NAME`; `settings.py` and `settings.config.ts` read both. No address, port, model id or price is written in code.
