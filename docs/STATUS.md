# Status

The pilot from `docs/PLAN.md` is built: all six phases are done. Insights, from `docs/PLAN_INSIGHTS.md`, is built: all three phases are done. The harness, from `docs/PLAN_HARNESS.md`, is being built: phases 1 to 4 of 7 are done.

## Built

- Configuration: `.env.defaults` (committed) holds every setting that isn't secret, such as hosts, ports, the database file and the model; `.env` holds the keys and overrides it; the environment overrides both. `models.toml` lists the models allowed, as `provider:model` with their prices. `settings.py` and `settings.config.ts` read them; a value can name another as `${NAME}`. Tests and the end-to-end run read `.env.defaults` alone.
- `backend/`: UnderCover's records in SQLite (all SQL in `backend/store/`), seeded from `data/` on first use, with read operations for the claims queue (each claim's state, latest decision and payment), one claim, a policy with its plan and add-ons, a customer with their claim history, the policy wording, the agent's instructions (`backend/instructions.md`, written as goals) and the handlers. The policy wording and the claims manual are split into their numbered sections: `list_sections` (each document's opening, its version and scope, is section 0), `search_documents` (the three sections that best match a query, by the words they share, a title's words counting three times) and `read_section`. The backend never reads `data/evals/` or `data/security/`.
- Runs (`backend/runs.py`): `start_run` (a mode, a cap and a model), `get_latest_run`, `write_todos`, `finish_run` and `record_usage` (each model call's tokens, cost and time). A run reports the claims it started and its usage. Stop, or a new run from the dashboard, marks a run still running as stopped.
- The claim workflow (`backend/workflow.py`): `start_claim` (in a running run, refused past its cap; a claim tried again counts once), `record_step`, `list_steps`, `decide_claim`, `pay_claim`, `sign_off_claim`, `fail_claim` and `decide_as_handler`. A claim moves from `waiting` to `in_progress`, then to `awaiting_sign_off` (approved over $1,000), `referred` or `decided`. A claim that fails goes back to `waiting`, with any unpaid decision cleared and the failure recorded as a step; on its second failure it is `left_for_handler`. A handler decides a referred claim or one left for them. A payment over $1,000 is refused until a handler signs off, and a referral waits for a handler to approve or decline it. Payments are recorded, not made.
- `agent/`: the UnderCover Agent: a queue agent (`run_queue(cap, model)`) that plans its run as a to-do list, hands each claim to a fresh claim agent through its `work_claim` tool, one at a time, and finishes with a summary for the handlers, after a check that it hasn't missed a claim within its cap (claims tried again, then new ones). Its instructions and the claim agent's are in `backend/instructions/`, written as goals. In modules: `api.py` (the backend's API), `tools.py` (the tools and the contexts they read: a claim agent's `ClaimContext`, the queue agent's `RunContext`), `middleware.py` (the step and usage recorders), `harness.py` (the model, `work_claim` and `run_queue`, which finishes its run whatever happens) and `config.py` (settings and models). It runs on OpenRouter, Anthropic or a local Ollama model, chosen by `MODEL_NAME`. It reads the claim, the policy and the customer through the API, searches the policy wording and the claims manual and reads the sections it needs (its prompt lists their titles, not their text), records its decision, and pays approvals of $1,000 or less. Every tool call, tool result and reply is recorded as a step, and every section read as a `section` step. `work_claim` works a claim in a run and reports in a line ("CLM-1001: approved $420.00, paid"); a provider error is retried twice, a claim is stopped after 30 model calls, and any failure, or a claim left undecided, goes to `fail_claim`, so one bad claim never stops a run. Each model call's tokens, cost (from `models.toml`) and time are recorded on the run. A refused payment comes back to the agent as text.
- Running the agent (`backend/runner.py`): `run_claim` (a claim, on a model), `run_queue` (a cap and a model), `list_models`, `get_agent` and `stop_agent` start the agent's command line as a separate process, one run at a time. Stop ends it at once and puts the claim being worked back to `waiting`, keeping its steps. A new run first returns any claim an earlier run left in progress.
- `dashboard/`: the claims desk, in the brand's colors with light and dark themes.
  - Queue: the agent bar (a model picker from `models.toml`, the number of claims, Run, Run all and Stop), a tile per state that filters the table, money totals, search, a type filter and a sortable table.
  - Claim: the claim in full (story, items, documents), the policy and customer, the decisions and payment, the sections the agent read, each opening in place, a live timeline of the agent's steps, Run and Stop, a sign-off form for payouts over $1,000, a form for a handler to decide a referred claim or one left for a handler, and failed attempts among the steps.
  - Insights: what the agent's work adds up to, refreshed every five seconds: straight through, time per claim, a timeline of the latest run (a bar per claim from its first step to its last, colored by decision), tool calls and refusals, claims waiting for a handler, the money, the agent's decisions by claim type, the tools it called, the policy sections it cited, and a table of every claim it worked.
  - Instructions: the queue agent's and the claim agent's instructions, and the policy wording.
- Insights (`backend/insights.py`): `get_insights` sums up the agent's work on the queue from the records already kept: claims decided, straight through (declined, or approved and paid by the agent), sign-offs, referrals, claims waiting for a handler, tool calls and the calls the backend refused, time per claim (first to last step of its latest run), money, decisions by claim type, tools and the policy sections cited.
- `e2e/`: Playwright tests of the queue, opening a claim, signing off a payout, deciding a referral, the agent's steps on a claim page and Insights, on their own backend (port 8001), dashboard (port 5174) and database (`e2e/undercover-e2e.db`, seeded fresh each run).
- `postman/`: a Postman collection and environment for the whole API, including a run through the workflow, the insights it adds up to, and starting and stopping the agent.

## Running it

- `npm run dev` starts the backend (`uv run -m backend`) and the dashboard on the hosts and ports in `.env.defaults`: by default the backend on port 8000, documented at `/docs`, and the dashboard on port 5173. On Windows the backend's auto-reload sees a change but can fail to restart, leaving the old code running; after pulling or switching branches, restart `npm run dev`.
- The database is the file named in `UNDERCOVER_DB`, `backend/undercover.db` by default. A database seeded before the claims manual was added has no manual: run `uv run -m backend.seed` after pulling. `uv run -m backend.seed` resets it to the data in `data/`.
- Run the agent from the dashboard (the agent bar's model, claims field, Run N and Run all, or Run the agent on a claim, on the model picked there), or from the command line with the backend running: `uv run -m agent CLM-1001` for one claim, `uv run -m agent --cap 5` for the queue agent on five claims (every waiting claim without `--cap`; `--cap` applies only to the queue), and `--model provider:model` for a model in `models.toml`. It calls the model in `MODEL_NAME`, one of those in `models.toml`: `openrouter:deepseek/deepseek-v4.1-flash` by default, the brief's choice. `MODEL_NAME` in `.env` overrides it, such as `anthropic:claude-haiku-5-5` (needs `ANTHROPIC_API_KEY`), `openrouter:openrouter/free` (free) or `ollama:qwen3.5:4b` (local and free).
- `npm run check` runs every check, and passes without `.env`. The end-to-end tests need ports 8001 and 5174 free. Guards in `tests/test_standards.py` and `dashboard/src/standards.test.ts` hold the code to `docs/CODE_STANDARDS.md`.
- `npx -y newman@6 run postman/undercover.postman_collection.json -e postman/undercover_local.postman_environment.json` runs the Postman collection against the backend on port 8000. Its Workflow folder changes claims, so reset the data first, and its Agent folder calls the model for a moment.
