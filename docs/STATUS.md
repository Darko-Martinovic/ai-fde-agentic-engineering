## Built

- Configuration: `.env.defaults` (committed) holds every setting that isn't secret, such as hosts, ports, the database file and the model; `.env` holds the keys and overrides it; the environment overrides both. `models.toml` lists the models allowed, as `provider:model` with their prices. `settings.py` and `settings.config.ts` read them; a value can name another as `${NAME}`. Tests and the end-to-end run read `.env.defaults` alone.
- `backend/`: UnderCover's records on Supabase's Postgres when `DATABASE_URL` is set (in `.env`), in the `undercover` schema, and in SQLite otherwise, as in the tests. The tables are SQLAlchemy Core `Table`s in `backend/db.py` and every query is a Core expression in `backend/store/`, written once for both. On Postgres each process keeps a pool of at most 3 connections (`DATABASE_CONNECTIONS`; the brief allows 4), the search path is set to the schema on every connection, and the tables have row level security on, with no policies, so Supabase's API roles can't reach them. Each request's work is one transaction, committed before the response. The records are seeded from `data/` the first time a process finds no tables, with read operations for the claims queue (each claim's state, latest decision and payment), one claim, a policy with its plan and add-ons, a customer with their claim history, the policy wording, the agents' instructions (`backend/instructions/queue.md` and `claim.md`, written as goals) and the handlers. The policy wording and the claims manual are split into their numbered sections: `list_sections` (each document's opening, its version and scope, is section 0), `search_documents` (the three sections that best match a query, by the words they share, a title's words counting twice) and `read_section`. `calculate_payout` works out an approval's payout on a claim's policy with UnderCover's payout rules (`backend/payout.py`, from `labs/week2day1_payout.py`: per-item and electronics limits, cash, hotel nights by the room, meals without receipts, what others paid, the deductible, the benefit maximum), step by step, and whether it needs a sign-off under the limit in `data/company.json`; it records nothing. The backend never reads `data/evals/` or `data/security/`.
- Runs (`backend/runs.py`): `start_run` (a mode, a cap and a model), `get_latest_run`, `write_todos`, `finish_run` and `record_usage` (each model call's tokens, cost and time). A run reports the claims it started and its usage. Stop, or a new run from the dashboard, marks a run still running as stopped.
- The claim workflow (`backend/workflow.py`): `start_claim` (in a running run, refused past its cap; a claim tried again counts once), `record_step`, `list_steps`, `decide_claim`, `pay_claim` and `fail_claim` (`backend/workflow.py`, the agent's moves), and `review_payout` and `decide_as_handler` (`backend/reviews.py`, the handlers'), following the rules in `backend/claim_rules.py`. A handler reviews a held payout with `review_payout`: a sign-off records who and when on the decision and puts the claim back in progress for the agent to pay, and the payment records the handler and the time of the sign-off; a rejection needs a note, which goes back to the agent, which decides again. After a rejection the agent's next decision always goes back to a handler (an approval of any size waits for a sign-off, anything else is referred), a second rejection refers the claim, and a failure after a rejection leaves the claim for a handler. Once a review is committed, a background task asks the agent's service to pick the claim up (`backend/agent_service.py`, at `UNDERCOVER_AGENT`); if the service can't be reached, the backend logs a warning and the review stands. A repeat of the agent's decision or of a payment already recorded, as when the agent carries on after a restart, returns the claim, and a different one is refused; a claim's `revision` makes sure two at once are recorded once. A claim reports its latest attempt's run and thread and how many attempts it has had. A claim moves from `waiting` to `in_progress`, then to `awaiting_sign_off` (approved over $1,000), `referred` or `decided`. A claim that fails before it is decided goes back to `waiting`, with the failure recorded as a step; on its second failure it is `left_for_handler`. A claim with a decision is never failed (the next run carries it on), except one whose payout a handler rejected, which is left for a handler. A handler decides a referred claim or one left for them. A payment over $1,000 is refused until a handler signs off, and a referral waits for a handler to approve or decline it. Payments are recorded, not made.
- `agent/`: the UnderCover Agent: a queue agent (`queue_agent.run_queue(cap, model, saver)`, on LangChain's `create_agent`) that plans its run as a to-do list, hands each claim to a claim agent through its `work_claim` tool, one at a time, and finishes with a summary for the handlers, after a check that it hasn't missed a claim within its cap (claims tried again, then new ones). The claim agent is a LangGraph graph of our own (`agent/graph.py`), as in `labs/week2day3.ipynb`: its state (`ClaimState`: the messages, the model calls made, and the decision and status the backend recorded), an `agent` node that calls the model with the tools bound, a `tools` node (LangGraph's `ToolNode`), a `wait_for_sign_off` node that pauses with `interrupt()`, and a `pay` node. The agent works the claim with its tools and records its decision with `decide_claim`, which ends its work; the graph then follows the backend's reply: it pays an approval the backend can pay at once, pauses when the backend says the approval waits for a sign-off, and ends on a decline or a referral. The agent has no `pay_claim` tool, and the graph never compares a payout with the limit. Its progress is saved after every step (`durability="sync"`) with LangGraph's synchronous Postgres checkpointer (`agent/checkpoints.py`) in the same Supabase schema, on a pool of at most 3 connections, its tables with row level security on; the command line needs `DATABASE_URL`, and the tests save in memory. Its instructions and the queue agent's are in `backend/instructions/`, written as goals. In modules: `api.py` (the backend's API), `tools.py` (the tools and the contexts they read), `graph.py` (the claim graph and its state), `checkpoints.py` (where it saves its progress), `recording.py` (the steps and usage the agents record), `middleware.py` (the queue agent's usage recorder and refusals), `harness.py` (the model, the claim graph for each claim and `work_claim`), `queue_agent.py` (the queue agent and `run_queue`, which finishes its run whatever happens) and `config.py` (settings and models). It runs on OpenRouter, Anthropic or a local Ollama model, chosen by `MODEL_NAME`. It reads the claim, the policy and the customer through the API, searches the policy wording and the claims manual and reads the sections it needs (its prompt lists their titles, not their text), works out an approval's payout with its `calculate_payout` tool and records its decision. Every tool call, tool result and reply is recorded as a step by the graph's nodes, and every section read as a `section` step. `work_claim(claim_id, run_id, model, saver)` works a claim in a run as a new attempt on a new thread and reports in a line ("CLM-1001: approved $420.00, paid"); a provider error is retried twice (the model's `with_retry`), a claim is stopped after 30 model calls (counted in its saved state), and a failure before the decision, or a claim left undecided, goes to `fail_claim`, so one bad claim never stops a run. A claim with a decision is never failed: an approval whose payment failed stays in progress ("not paid yet"). Each model call's tokens, cost (from `models.toml`) and time are recorded on the run. A refusal from the backend, or a tool called the wrong way, comes back to the agent as text.
- Tracing (`agent/tracing.py`): every run of the agent is traced in Langfuse, from the keys in `.env` (`LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`; `LANGFUSE_BASE_URL` and `LANGFUSE_TRACING_ENVIRONMENT`, `development`, are in `.env.defaults`). Each claim worked is a `work-claim` trace of its own, input the claim and output its report, with the claim agent (`claim-agent`) inside it, in the session named after the claim's thread (such as `CLM-1001-b325c560`), so everything done on one claim is found together. It is its own trace even inside a queue run, because the harness runs it in a fresh context. A queue run is one `run-queue` trace: its input is what the queue agent was asked and its output the summary, with the queue agent's model calls and tools, each `work_claim` call showing the claim's report. Every model call is a generation with the model, tokens and cost; LangChain's middleware hooks are left out. A run ended by Stop leaves its trace unfinished. Without the keys nothing is sent and Langfuse warns that it's off; the tests never send.
- The agent's service (`agent/service.py`, `uv run -m agent.service`, on `AGENT_HOST` and `AGENT_PORT`, 8002): `health` and `resume_claim`, which the backend calls after a handler's review. It answers 202 at once and carries the claim on in a background task with `harness.carry_on`, on `MODEL_NAME`, printing the claim's report: after a sign-off the graph resumes past its pause and pays (no model call); after a rejection the handler's note reaches the agent as a message and it decides again. It refuses (409) a claim that isn't in progress. Its lifespan keeps the checkpointer open. A carry-on is a `carry-on` trace in the claim's session, beside the `work-claim` trace from before the pause.
- Running the agent (`backend/runner.py`): `run_claim` (a claim, on a model), `run_queue` (a cap and a model), `list_models`, `get_agent` and `stop_agent` start the agent's command line as a separate process, one run at a time. `run_claim` takes a waiting claim, or one a stopped run left in progress, which the run carries on. Stop ends the process at once and marks its run stopped; the claim it was working stays in progress with its saved progress, and so does one whose process ended any other way. On a claim's page, Carry on runs the agent on such a claim.
- `dashboard/`: the claims desk, in the brand's colors with light and dark themes.
  - Queue: the agent bar (a model picker from `models.toml`, the number of claims, Run, Run all and Stop, and the model a running agent is on), the latest run as it happens (its model, claims done out of its cap, the time taken and left at the pace so far, model calls, tokens and cost, the claims it started, the queue agent's to-do list, the claim being worked with its latest attempt's steps arriving live, and the summary for the handlers once it finishes; a run started from the command line shows here too, and a run whose process was killed outside Stop shows as live until the next Run or Stop marks it stopped), a tile per state that filters the table, money totals, search, a type filter and a sortable table.
  - Claim: the claim in full (story, items, documents), the policy and customer, the decisions and payment, the sections the agent read, each opening in place, a live timeline of the agent's steps, Run and Stop, a review form for a held payout (Sign off, or Reject with a note for the agent), a form for a handler to decide a referred claim or one left for a handler, and failed attempts among the steps.
  - Insights: what the agent's work adds up to, refreshed every five seconds: straight through, time per claim, a timeline of the latest run (a bar per claim from its first step to its last, colored by decision), tool calls and refusals, claims waiting for a handler, the money, the agent's decisions by claim type, the tools it called, the policy sections it cited, and a table of every claim it worked.
  - Instructions: the queue agent's and the claim agent's instructions, and the policy wording.
- Insights (`backend/insights.py`): `get_insights` sums up the agent's work on the queue from the records already kept: claims decided, straight through (declined, or approved and paid by the agent), sign-offs, referrals, claims waiting for a handler, tool calls and the calls the backend refused, time per claim (first to last step of its latest run), money, decisions by claim type, tools and the policy sections cited.
- `bench/`: the model comparison, apart from the product. For each trial in `bench/plan.toml` (a model, the 25 claims or the five `tiny` ones, a number of runs) it reseeds, works the claims through the harness, reads each claim's decision and payout and the run's usage through the API, and scores them against the handlers' decisions in `data/evals/decisions.json`: the decision, and an approval's payout within a dollar. Only `bench/score.py` reads `data/evals/`, and a test checks it. Runs are kept in `bench/results.json`; a run the provider refused outright is tried again and not scored. It refuses to pass `BENCH_BUDGET_USD` ($10). It writes `bench/results.md` and the chart `bench/results.svg`.
- `e2e/`: Playwright tests of the queue, opening a claim, a sign-off and a rejection reaching the agent's service (a stand-in for it, `e2e/agent-stand-in.ts`, on port 8003), deciding a referral, the agent's steps on a claim page, Insights and the run panel following a run, on their own backend (port 8001), dashboard (port 5174) and database (`e2e/undercover-e2e.db`, seeded fresh each run).
- `postman/`: a Postman collection and environment for the whole API, including a run through the workflow, the insights it adds up to, and starting and stopping the agent.

## Running it

- `npm run dev` starts the backend (`uv run -m backend`), the agent's service (`uv run -m agent.service`) and the dashboard on the hosts and ports in `.env.defaults`: by default the backend on port 8000, documented at `/docs`, the agent's service on port 8002 and the dashboard on port 5173. On Windows the backend's auto-reload sees a change but can fail to restart, leaving the old code running; after pulling or switching branches, restart `npm run dev`.
- The database is Supabase when `.env` has `DATABASE_URL` (the session pooler's connection string), and otherwise the SQLite file named in `UNDERCOVER_DB`, `backend/undercover.db` by default. `uv run -m backend.seed` resets the backend's tables in whichever it is to the data in `data/` ("Reset the undercover schema on Postgres"), leaving any other tables alone. The tests and the end-to-end run never read `.env`, so they always use SQLite. The agent needs Supabase: it saves its progress there, so without `DATABASE_URL` the agent's service doesn't start and a run, from the dashboard or the command line, stops before it begins; the backend and the dashboard still work on SQLite.
- Work survives a restart. Every run, from the dashboard or the command line, first finishes the latest run if it is still running ("The run stopped before it finished.") and carries on every claim left in progress, printing each report, before its own work: a claim the agent was stopped on carries on from its last saved step on the same thread, without a new attempt, and a claim signed off while the agent's service was away is paid. These don't count toward the run's cap. With nothing waiting, `uv run -m agent` still carries them on, then prints "No claims are waiting." A claim that fails while carried on goes back in the queue and starts afresh on a new thread, as before. A claim that can't be picked up at all, such as one whose decision was made through the API so the graph saved nothing, is reported ("not picked up") and stays in progress for a handler to look at; it never stops a run. As before, two processes can't tell a stopped claim from one the other is working at that moment: don't start a run from the terminal while one runs from the dashboard, and Carry on on a claim's page runs the agent, which carries on every claim left in progress, not only that one.
- Run the agent from the dashboard (the agent bar's model, claims field, Run N and Run all, or Run the agent on a claim, on the model picked there), or from the command line with the backend running: `uv run -m agent CLM-1001` for one claim, `uv run -m agent --cap 5` for the queue agent on five claims (every waiting claim without `--cap`; `--cap` applies only to the queue), and `--model provider:model` for a model in `models.toml`. It calls the model in `MODEL_NAME`, one of those in `models.toml`: `openrouter:deepseek/deepseek-v4.1-flash` by default, the brief's choice. `MODEL_NAME` in `.env` overrides it, such as `anthropic:claude-haiku-5-5` (needs `ANTHROPIC_API_KEY`), `openrouter:openrouter/free` (free) or `ollama:qwen3.5:4b` (local and free).
- `uv run -m bench` runs the model comparison against the backend on port 8000, with the dashboard's agent idle: it resets the database before each run, so reseed or run it on data you don't need. `--estimate` prints what it would cost and stops; `--report` rewrites the report from the runs saved.
- `npm run check` runs every check, and passes without `.env`. The end-to-end tests need ports 8001, 5174 and 8003 free. Guards in `tests/test_standards.py` and `dashboard/src/standards.test.ts` hold the code to `docs/CODE_STANDARDS.md`.
- `npx -y newman@6 run postman/undercover.postman_collection.json -e postman/undercover_local.postman_environment.json` runs the Postman collection against the backend on port 8000. Its Workflow folder changes claims, so reset the data first, and its Agent folder calls the model for a moment.
