# Code standards

## General

1. Keep it simple, do not overcomplicate.
2. Comments only when necessary.
3. Be concise: a short README and no emojis.
4. IMPORTANT: avoid overly defensive code. Handle exceptions only when necessary.
5. Use uv: ALWAYS `uv run`, NEVER `python3`.
6. TypeScript: strict mode, never `any`.

## Structure

7. One way to do each thing. The agent reaches the backend only through its two clients, `agent/api.py` for the claim agent and the service and `agent/improver_api.py` for a round of improvement, both on the one connection in `agent/connection.py`, and the dashboard only through `dashboard/src/api.ts`, each with one function per backend operation, named after it; the backend reaches the agent's service only through `backend/agent_service.py`, the judge only through `backend/judge.py` and Supabase Auth only through `backend/auth.py`, and the dashboard reaches Supabase only through `dashboard/src/auth.ts`. The base URL and each path are written once, there, and no other module builds a URL or sends a request.
8. Each module has one job, and its name says what it is. A module uses another through what that module is for, and never borrows its helpers. A helper two modules need goes in a module of its own. No circular imports. Tests follow the same rule: shared test helpers live in their own module, never in another test file.
9. Write a literal once. A URL, a path, a status or a message used in more than one place is named once, in the module that owns it.
10. Use the framework's own way before writing your own: FastAPI dependencies and models (`HTTPBearer` for sign-ins), PyJWT's `PyJWKClient` for Supabase's keys, LangChain's `context_schema` with `ToolRuntime` for what a tool needs to know, `create_agent` with `HumanInTheLoopMiddleware`, `ModelCallLimitMiddleware` and its hooks for the improver, LangGraph's `Send`, `max_concurrency`, `RetryPolicy` and `Runtime` context for the dispatcher, `PostgresSaver` and `Command(resume=...)` for a pause, `init_chat_model` for models, the `openrouter` client's own timeout for the judge, with its retries off, `difflib` for diffs, `supabase-js` sessions, React hooks, context and shared components, and Playwright's `storageState`. Check the documentation for the installed version. Where we write our own instead, the plan says why.
11. A function does one job. Split one that mixes levels of detail, such as setting up a run, driving the agent and recording the result.
12. When you extend code, bring it up to these standards first. Never copy a pattern they rule out.

## The agent

13. The agent has six parts, kept apart, and their supports. `api.py` is the backend's API for the claim agent and the service, with no way to the scores, the settings, the rounds or the handlers' decisions. `tools.py` holds every tool of the claim agent and the context the tools read. `harness.py` builds and runs the claim agents: their models, their graphs and their work on a claim. `dispatcher.py` works a dispatch or an evaluation with many claim agents at once, and reaches the claim agent only through the harness's one function, `work_in_run`. `service.py` is the agent's service, which the backend calls to start and stop a run, to start a round of improvement and pass on a review of the improver's proposal, and after a handler's review of a payout; `service_models.py` holds what it's asked and answers, and `run_lock.py` the lock that lets one run or round work at a time. `improver.py` is the improver, a LangChain `create_agent` with its four tools and its middleware, which reaches the backend through `improver_api.py` and claim agents only through the function the service hands it; `rounds.py` works a round in the service: its first evaluations, the improver's stretches between reviews and its finish. `graph.py` is the claim agent's graph, whose nodes record each step and model call, and whose first node runs the security check in `screening.py`, outside the claim agent's configuration; `recording.py` holds what they record on the backend, `reports.py` the line each piece of work on a claim reports, `checkpoints.py` where the claim graph saves its progress, `tracing.py` traces the claims and the improver's stretches in Langfuse, `versions.py` holds a version of the claim agent's configuration as the harness builds it, and `connection.py` holds the one connection to the backend that the agent's clients share. Rules about claims and payments are enforced by the backend, whatever the agent does.
14. Instructions give an agent its goal, what it has to work from and what done looks like. They don't script its steps: it plans those itself. Anything that must always happen, or happen in a fixed order, is done by the code.

## Checked by tests

Except where marked, these hold because a test fails when they don't: `tests/test_standards.py` for the Python parts and `dashboard/src/standards.test.ts` for the dashboard and the TypeScript config. A guard that is in the way is a sign the design is wrong, never a reason to loosen the guard.

15. One owner for each service's address. In the agent, `httpx`, `UNDERCOVER_API` and the agent's key appear only in `agent/connection.py` and `/api/` paths of the backend only in `agent/api.py` and `agent/improver_api.py` (the agent's service declares its own routes under its `/api` router), and the claim agent's modules (`tools`, `graph`, `harness`) never import `improver_api`; in the backend, Supabase Auth's address only in `backend/auth.py`, the judge's only in `backend/judge.py`, and `MODEL_NAME` only in `backend/free_model.py`; in the backend, `httpx` and `UNDERCOVER_AGENT` only in `backend/agent_service.py`; in the dashboard, `fetch` and `/api/` paths only in `api.ts`, and `@supabase/supabase-js` only in `auth.ts`.
16. One name for each operation: each function in `agent/api.py` is named after a backend `operation_id`, each key of `api` in `dashboard/src/api.ts` is the same name in camelCase, and each Postman request's description starts with its operation, every operation having at least one request.
17. `backend/main.py` only puts the app together. Routes live in one router per resource (claims, records, handlers, documents, configuration, platform settings, workflow, usage, reviews, runs, evaluations, improvement, rounds and insights), and no router imports another. All SQL lives in `backend/store/`, one module per group of tables, each function named for what it returns or does; routes and other modules call those functions, never the database. `backend/db.py` holds the schema, with `backend/db_improvement.py` for the tables that improve the claim agent and `backend/schema.py` for what they share. The one other place is `agent/checkpoints.py`, which opens the claim graph's checkpointer: LangGraph makes its own tables, and the module makes the schema for them and turns row level security on for them.
18. Size: a module stays under 300 lines and a function under 40, or 120 for a React component. Past that, split it. ESLint enforces `max-lines` 300, `max-lines-per-function` 120 and `complexity` 10; ruff enforces mccabe 8; tests check each Python module's and function's length.
19. Page links are built in one place, `dashboard/src/paths.ts`, which also reads them back.
20. Tests mirror modules: a test file per module it tests, shared helpers in `conftest.py` or `dashboard/src/testing.ts`. (Checked by review.)
21. Names say what a thing is, never how it's built: no `utils`, `helpers`, `misc` or `common` modules. (Checked by review.)
22. Configuration comes from the environment, filled in from `.env` and then `settings/.env.defaults` by `settings/__init__.py` (Python) and `settings/settings.config.ts` (TypeScript), and the models the claim agent may use come from `data/models.json`, through the backend. A value can name another as `${NAME}`, so each host and port is written once. No host, port, URL, model id or price is written in code: the judge is `JUDGE_URL` and `JUDGE_MODEL`, the improver `IMPROVER_MODEL` and `IMPROVER_REASONING_EFFORT`, and the platform's settings (the approval limit, and what a round works to) are records in the backend, seeded from `data/company.json` and `data/improvement.json`; the dashboard's Supabase project is `VITE_SUPABASE_URL` in `.env`. Tests and the end-to-end run read `settings/.env.defaults` alone, so `npm run check` never needs `.env`.
